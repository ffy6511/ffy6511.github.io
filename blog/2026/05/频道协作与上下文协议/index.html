Conversation-first 协作模型#

Poco 的协作从 server 里的 channel 或 DM 开始. 人类和 Agent 先在这里形成对话. Task、thread、Agent run 和 artifact 都从 conversation 派生, 并保留来源关系.

频道是这些对象共同发生的上下文容器: 人类、Agent、工作项、线程、共享成果和结构化动作都留在同一段对话里.

协作对象#

下图是协作对象从 server 到一次执行结果的派生关系. 蓝色的 Conversation 是频道和 DM 共用的容器.

Server 是团队边界. Channel 和 DM 都是一等 conversation, 差别在参与者范围. Message 是协作的原子事实. Thread 把局部讨论留在原始消息旁边. Task 是从某条消息或线程显式派生的工作项. Agent run 由消息触发, 并绑定在当前 conversation 的范围内.

对话可以先发生#

Task 如果是第一入口, 频道消息、thread、DM、mention 和 Agent profile 都会变成 task 的附属能力. 使用方式会回到 issue-first: 用户在某张工作单里评论, 协作发生在工单内部.

Conversation-first 允许讨论先发生, 结构化工作项按需出现. 用户可以只讨论, 也可以把某条消息转成 task. 可以在公开频道触发 Agent, 也可以通过 DM 和某个 Agent 单独沟通. 系统不要求所有互动先变成 task.

Thread、DM 和 task#

Thread 收束局部上下文. 一条消息下的追问、澄清和执行结果留在这根消息附近, 不必把整个频道切成多个独立空间. Thread 不建立新的权限边界, 它仍然属于原来的 conversation.

DM 解决参与者范围. 用户可以和另一个人或某个长期 Agent 单独沟通, 不把这段对话放进公开频道. DM 和 channel 都是一等 conversation, 所以消息、thread、Agent run 和 task 的派生规则可以共用同一套模型.

Task 负责结构化推进. 讨论形成明确工作项时, 它才被显式创建. Task 的状态变化回到原始 thread, “讨论为什么变成任务” 和 “任务后来怎样推进” 留在同一条历史上.

从消息到 task#

一条消息只有在形成明确工作项时才进入 task 流. 最小状态是四段: todo、in_progress、in_review、done. Task 保留来源 message 和 thread, 后续状态变化、评论和执行结果都能回到原始上下文.

下图是 “创建为 task” 之后, 频道里多出来的两类消息.

Task 承担团队可见工作项的状态流转. 临时讨论、澄清、reaction 和 Agent 输出仍然留在 conversation 里.

从消息到 Agent run#

用户在频道里 @agent 时, 系统先保存原始消息, 再匹配目标 Agent, 然后创建带有 conversation scope 的 run. 这个 run 带上 server、channel、message、thread 和目标 Agent 的索引, 并在频道里生成一个执行投影.

绑定之后, Agent 能做三件事:

  • 通过受控工具读取当前频道和线程上下文.
  • 把结果回写到同一个 conversation.
  • 在需要时创建 task、发布 artifact, 或请求另一个 Agent 协作.

Agent run 的入口在频道里. 完整执行细节不必全部刷进主消息流. 主消息流保持协作可读, 执行详情进入独立抽屉或回放视图.

五个对象#

对象核心职责
Server名称、成员、所有者.
Conversationserver、类型、可见性、成员.
Messageconversation、作者、正文、thread root.
Channel taskconversation、来源 message、状态、负责人.
Agent runconversation、触发 message、目标 Agent、运行状态.

Task 和 run 必须能追溯到来源 conversation 和 message. DM 和 channel 都是 conversation. Thread 不创建新的协作空间, 只在同一 conversation 内收束局部上下文.

取舍#

方案问题Poco 的选择
Task-first讨论、DM、thread 和 Agent run 都依附 task, 协作入口变窄.不采用.
Issue / board 继续做主线新旧语义长期并存, 频道只是旧模型的外壳.不采用.
Conversation-first需要重新建模消息、task 和 run 的关系, 协作入口更直接.采用.

协作事实先保存在真实对话里, 再按需要派生结构化对象.

触发信封与渐进式上下文读取#

在频道协作里, @agent 把一条普通频道消息变成一次可执行、可追踪、可恢复的 Agent run. 频道里的材料不能全部塞进 prompt. Agent 也不能默认自己已经拥有完整上下文.

触发信封划定这条边界. 用户的原始请求作为正文进入 Agent. 系统上下文以结构化索引进入运行配置. 频道事实仍由 Backend 掌握. Agent 需要更多信息时, 再通过受限工具按需读取消息、线程、任务、共享成果或其他 Agent 的信息.

系统因此知道一次触发来自哪里、指向哪个 Agent、引用了哪些上下文、是否由另一个 Agent 转交, 以及后续读取是否仍在权限范围内.

信封在两层之间#

触发信封位于频道层和执行层之间. 频道层保存真实协作状态, 执行层运行模型和工具, 信封把两者接起来.

下图是一条频道消息怎样拆成正文和信封, 再在需要时回到 Backend.

  • trigger body 是用户写下的原始内容, 保持自然语言.
  • AgentTriggerEnvelope 是系统生成的结构化索引, 用来定位 server、channel、message、thread、目标 Agent 和引用材料.
  • 频道状态不属于模型 session. 消息、任务、共享成果和成员关系回到 Backend 读取.

信封保存上下文的索引和权限边界.

正文和系统索引入开#

把最近消息、线程、共享文件摘要、Agent 说明和系统规则一次性拼进 prompt, 在演示阶段成本低. 进入多 Agent 协作后, 会出现三个问题.

正文和系统上下文混在一起. 用户到底说了什么、系统补了什么、哪些信息来自历史消息, 回放时分不清.

权限和时效变得模糊. 运行开始时复制进去的频道快照, 未必还是运行过程中的最新状态, 也未必仍满足当前成员权限.

协作链路难以校验. 一个 Agent 请求另一个 Agent 时, 如果只靠自然语言 mention, 普通提及和真实调度分不开, 也难以防止重复触发和循环转交.

Poco 把触发输入拆成两部分. 正文只放请求本身. 信封只放定位和控制信息. 模型需要更多上下文时, 必须显式读取.

信封保存什么#

触发信封是一次 Agent run 的协作地址簿. 它不复制频道内容, 只保存足够的索引, 让运行时回到权威状态源读取.

字段组设计作用
触发类型区分频道 mention、Agent DM、Agent-to-Agent 协作等来源.
协作空间记录 server 和 channel, 限制后续工具读取的范围.
消息位置记录触发消息和线程根消息, 让 Agent 能回读上下文.
目标 Agent记录这次触发要交给哪个持久化 Agent.
来源角色区分触发者是用户、Agent 还是系统.
引用对象保存被显式引用的消息、任务或共享成果.
转交信息保存父 run、转交深度和去重键, 用来防止协作循环.

信封不保存完整 thread、artifact 内容或最近消息列表. 它更像索引时, 才容易被持久化、回放、迁移和审计. 它如果变成上下文快照, 就会成为另一层不可控的 prompt 拼接.

一次触发怎样进入运行时#

@reviewer 看一下这段 API 错误处理 可以拆成下面几步. 蓝色步骤写事实或做校验, 黄色步骤负责入队和派发, 橙色步骤在沙箱里运行.

Executor 放进运行配置的是提示和契约: 本次请求是什么, 触发来自哪里, 需要上下文时走哪些工具. 频道事实仍然保存在 Backend.

Agent 的工作顺序是:

  • 先根据用户正文理解任务.
  • 需要完整线程时, 读取线程.
  • 需要共享成果时, 读取频道成果树.
  • 需要其他 Agent 协助时, 发起结构化协作请求.
  • 工具返回权限错误或对象不存在时, 不能当作已经读过.

渐进式读取#

渐进式读取减少无关上下文. 更重要的作用是让频道状态保持可信.

Agent 不自己携带 server、channel 或身份参数去读数据. 运行时工具根据当前 run 的会话范围解析这些信息, 再由 Backend 校验是否仍然允许读取.

下图是一次频道工具调用的校验顺序. 粉色的错误在任一关失败时返回, Agent 不能把这次调用当成已经读到内容.

Agent 无法通过编造 channel id 或 artifact id 来越权读取. 读取动作本身可以被记录: 系统知道 Agent 最终回答了什么, 也知道它是否读过某条线程、某个共享成果或某个任务.

统一的频道工具网关#

频道工具如果按功能零散注入, Executor 会逐渐长出多个 __poco_channel_* server. 每个 server 自己解释 session、channel、agent 和权限, 又会回到多处拼上下文、多处判权限.

Poco 的目标结构是: Executor 只注入一个内置频道运行时 MCP server. 所有频道协作工具都挂在同一个运行时工具面下. 工具内部可以按资源域拆分客户端. 对 Agent 来说, 面对的是同一个 channel-scoped contract.

下图把六个资源域收成一个节点. 它们共用运行时客户端, 再经 Manager 代理到达 Backend.

这层网关承担两类职责.

  • 对 Agent: 提供稳定、可解释的工具名称和输入契约, 让 Agent 知道何时读消息、何时读共享成果、何时创建任务、何时请求另一个 Agent.
  • 对系统: 把 session_id 解析成 server、channel 和 agent identity, 再由 Backend 做成员校验、生命周期校验和资源范围校验.

频道工具不接受 server_id、channel_id 或当前 agent_identity_id 作为普通参数. Agent 可以选择要读哪个 message、artifact 或 task, 不能自己声明属于哪个频道.

工具暴露哪些能力#

频道工具不暴露底层表结构. 它们围绕协作对象提供少量稳定能力: 读消息、读共享成果、发现可协作 Agent、发起协作、操作频道任务, 以及添加或撤销 reaction.

类型代表能力设计作用
读取类工具消息、thread、共享成果、频道 Agent、频道任务.Agent 回到 Backend 读取权威事实.
写入类工具请求另一个 Agent、创建或更新频道任务、添加或移除 reaction.协作副作用写回频道事实源.

工具粒度比工具数量更要紧. 消息读取收敛到 read_channel_messages. 共享成果保留 list、search 和 read. Agent 协作收敛到 request_agent_collaboration. “请另一个 Agent 总结” “请另一个 Agent 审查” “请另一个 Agent 接手修复” 都通过可见回复和最小请求文本表达, 不再各做一个动词工具.

工具面因此覆盖四条路径: 理解上下文、复用材料、转交任务、更新团队状态. 每一种协作说法不单独变成新工具.

read_channel_messages#

read_channel_messages 是渐进式读取里最容易偏离设计的工具. 它如果只支持读取 thread, Agent 在需要频道前文时会误判上下文不足. 它如果默认读取全频道, 又会回到大 prompt.

它用 selector 表达读取意图:

  • 已知消息用 message_ids.
  • thread 用 thread_root_message_id.
  • 频道前后文用 anchor_message_id 加 direction.
  • 近期上下文用无 selector 的默认读取.
  • read_all = true 只作为显式选择, 用于小频道、调试和复盘.

默认路径保持克制. 常规协作优先使用 message id、thread root 或 anchor 翻页. 只有 Agent 明确需要全量频道历史时, 才使用 read_all. 返回结果携带 reply count 和 reaction 聚合, 不必再为消息状态单独做一个读取 reaction 的工具.

协作转交怎样防循环#

Agent-to-Agent 协作是触发信封的常见风险点. 一个 Agent 在回复里写 @reviewer, 不会自动触发另一个 Agent. 普通文本提及和真实调度没有稳定边界.

协作转交是结构化动作. 当前 Agent 必须给出目标 Agent、请求正文、协作模式和引用材料. Backend 再做几类校验:

  • 目标 Agent 必须存在, 并且仍在当前频道中处于可协作状态.
  • 目标 Agent 不能是当前 Agent 自己.
  • 转交深度有限, 避免 Agent 之间无限互相调用.
  • 同一次会话、同一个目标、同一种协作模式可以去重, 避免重复创建 run.
  • 新 run 保留父 run 和原始线程关系, 方便回放协作链路.

协作意图因此是系统可以校验、排队、取消和追踪的副作用.

任务和 reaction 用同一原则. Agent 在普通回复里写 “我已经认领任务”, 不算完成认领. 用自然语言说 “我给这条消息点了赞”, 也不算 reaction 成功. 只有对应的结构化工具调用成功, 这些状态才进入频道事实源.

五个抽象#

对象核心职责
Channel message保存原始消息、作者、频道和线程关系.
Trigger envelope保存触发类型、协作空间、触发消息、目标 Agent、引用和转交信息.
Run snapshot保存本次运行的 prompt 正文、目标 Agent、信封和会话范围.
Channel runtime client把消息、成果、Agent、任务和 reaction 工具收在同一条运行时访问面上.
Channel tool gateway根据 run scope 校验权限, 再读取或写入频道状态.

这五层分别回答: 用户说了什么, 这次触发从哪里来, 执行时带着什么契约, 运行时有哪些受控工具, 后续怎样读取或写入权威状态.

取舍#

方案问题Poco 的选择
拼一个大 prompt用户正文、系统规则、历史消息和共享材料混在一起, 难以回放和审计.不采用.
完全依赖 SDK session模型 session 不知道最新频道状态和权限变化.不采用.
每次触发复制完整频道快照快照可能过大, 也会固化过期权限和无关内容.不采用.
给每种协作语义单独设计工具工具面膨胀, Agent 难以判断该用哪个动作.不采用.
多个频道 MCP server 分散注入鉴权、session 解析和错误语义会重复实现.不采用.
触发信封 + 渐进式读取需要维护协议和工具边界, 输入清楚、权限可控、状态可信.采用.

自然语言请求归正文. 协作索引归信封. 频道事实归 Backend. 扩展上下文归工具读取.

频道共享成果树与 Artifact 协议#

频道协作不能只共享聊天消息. Agent 运行中生成的计划、检查清单、报告和代码分析, 往往会成为后续协作的主要上下文. 这些材料如果只留在某次 session workspace 里, 其他人和别的 Agent 就只能靠复制粘贴继续工作.

Poco 建立 published artifacts 边界. 运行中产生的协作成果登记到频道共享成果树. 同频道成员和同频道 Agent 通过受控读取协议访问.

什么进入共享树#

下图上面一条是会进入共享树的路径. 下面三种材料用虚线接到 “不进入共享树”: 私有状态、临时快照和本地挂载都不自动发布.

共享成果树只收协作成果. 这个边界避免把长期记忆、本地授权目录和临时执行输入暴露给整个频道.

三类材料不能放进同一个可写目录#

一个共享可写文件系统会把三类边界混在一起.

Session workspace 是一次运行的工作区, 适合导出和归档, 不适合作为频道的长期公共盘.

Agent private state 保存长期记忆和偏好, 不应被其他 Agent 随意读取.

Local mount 是用户对某次 session 的本地目录授权, 不因为频道成员关系而扩散.

这三类如果合成一个可写目录, 会立刻遇到并发写冲突、私有状态泄露、本地目录暴露和 owner 权限不清.

成果怎样被发布#

发布时要保留来源: artifact 属于哪个 channel, 来自哪个 session, 由哪个 Agent 或用户发布, 逻辑路径是什么, 是否可预览, 内容类型是什么. 下图是从导出到后续读取的顺序. 文件内容进对象存储, 共享树只登记元数据.

后续读取时, Agent 不拿容器路径, 而拿 artifact id 或 logical path 作为受控标识.

Agent 的三个读取工具#

共享成果树对 Agent 暴露三个最小工具:

工具用途
list_channel_artifacts建立当前频道可读材料的索引.
search_channel_artifacts按名称、逻辑路径、来源或文本检索目标材料.
read_channel_artifact按 artifact id 或 logical path 读取内容或元数据.

这三个工具只读, 并且限定在当前 scope. Agent 不传 server 或 channel 身份, 也不能把 logical path 当作 /workspace 路径. 运行时根据当前 session scope 解析身份, Backend 再校验频道成员关系和 artifact 归属.

读取时的权限#

Agent 读取某个 artifact 时, 权限分成三步:

  • 系统从当前 run 的 session scope 解析 server、channel 和 Agent identity.
  • Backend 检查这个 Agent 是否仍是当前 channel 的 active member.
  • 校验通过后, 读取才落到频道的 published artifact 索引和对象存储.

这条链路里没有 “找不到就去 workspace 兜底”. 兜底读取会打破共享边界: Agent 可能读到未发布的 workspace 文件、private state, 甚至被引向 local mount. 发布进入公共树, 读取只读公共树, 未发布材料对频道不可见.

四个对象#

对象核心职责
Workspace manifest描述一次运行导出的文件集合.
Artifact metadata保存 channel、source run、logical path、mime type 和大小.
Object storage key指向真实内容, 避免把文件内容塞进消息表.
Runtime read gateway按 session scope 校验, 并返回内容或元数据.

只从 published artifacts 读取, 不从 session workspace、private state 或 local mount 兜底.

取舍#

方案问题Poco 的选择
频道共享可写文件系统权限扩散、并发写冲突、私有状态泄露和本地目录暴露.不采用.
只共享聊天消息Agent 无法稳定复用共同成果, 材料会反复复制粘贴.不采用.
Published artifacts + 只读读取协议需要维护索引和读取工具, 共享、授权和审计边界清楚.采用.

Poco 先把可共享的协作成果做实. 如果以后确实需要多人同写一份共享工作区, 再单独建 channel workspace.

延伸阅读#

  • 触发信封与渐进式上下文读取: Agent 读取共享成果时, 范围来自触发信封里的 channel scope.
  • GitHub Actions: Store and share data with workflow artifacts: CI 系统怎样登记可下载、可共享的运行产物.
  • SLSA provenance: artifact 的来源、构建过程和可追溯元数据.
  • in-toto Attestation Framework: 产物证明和元数据绑定.

结构化频道动作与 Agent 协作#

频道里的 Agent 需要能创建团队可见的 task、推进 task 状态、评论进展、读取消息和成果, 也需要在合适时请求另一个 Agent 协作. 这些副作用走结构化动作, 不靠解析模型文本.

Poco 把 Agent 的频道副作用收到 channel-scoped tools. Agent 可以在可见回复里解释意图. 只有工具调用成功, 系统才认为任务被创建、reaction 被添加, 或另一个 Agent 被触发.

工具围绕协作对象#

下图是一次 Agent run 可以走的四类频道动作. 具体工具名留在正文, 图上只标动作落在哪类对象上.

这些工具都绑定当前 session scope. Agent 不传入 server id、channel id 或 actor identity. 系统从 run snapshot 和 trigger envelope 解析当前协作空间.

四类动作对应的工具是:

  • 读上下文: read_channel_messages, 以及成果的 list、search、read.
  • 任务: 创建、认领、更新状态、评论.
  • Reaction: add_channel_message_reaction 和 remove_channel_message_reaction.
  • 协作: request_agent_collaboration.

工具调用之后事实写在哪里#

结构化工具是 Agent 进入频道领域的入口. 事实仍然落在对应服务里:

  • Task 工具进入 channel task service.
  • Reaction 工具进入 message reaction service.
  • Collaboration 工具进入 trigger service.
  • Artifact 工具进入 artifact read gateway.

工具层保持薄封装. 它做参数校验、scope 注入和错误格式化, 不重复实现业务规则. 业务约束由领域服务统一处理, 例如 task 状态是否合法、目标 Agent 是否还在频道中、reaction 是否已经存在.

可见回复和真实触发#

Agent 可以在频道里写: “我建议让 @api 补充认证链路细节.” 这只是可见文本, 不会自动触发 @api. 它如果真要请求协作, 必须调用结构化工具.

下图把两条出路分开. 上面的可见回复停在 “不创建 run”. 下面的结构化请求经过校验后才会入队.

普通 @handle 文本不会误触发. 真实触发也不会藏在无法审计的自然语言里.

任务操作也走工具#

Agent 内部的 todo 是执行计划. channel task 是团队协作对象. 两者不自动等价:

  • 要把工作变成团队可见任务, Agent 调用 create_channel_task.
  • 要更新团队状态, Agent 调用 update_channel_task_status.
  • 要记录进展, Agent 调用 comment_on_channel_task.

结构化 task 操作带来三点:

  • 状态只能在允许的集合里变化, 例如 todo、in_progress、in_review、done.
  • 状态变化会生成系统消息, 保留 actor、task 和 thread 关系.
  • Agent 只能操作当前 channel scope 内的 task, 不能跨频道写入.

Reaction#

Reaction 表示某个用户或 Agent 对某条消息的轻量反馈. 它被建模为 message x emoji x actor 的独立关系, 不改写消息正文, 也不是触发 Agent 的事件.

Agent 通过 add_channel_message_reaction 或 remove_channel_message_reaction 表达这种反馈. 工具成功后, 消息聚合展示 reaction. 工具失败时, Agent 不能声称已经贴过 reaction.

协作防循环#

Agent-to-Agent 协作有几条硬约束:

  • 目标 Agent 必须是当前频道的 active member.
  • 目标 Agent 不能是当前 Agent 自己.
  • 转交深度有限, 避免链式调用失控.
  • 同一来源、同一目标、同一模式使用 dedupe key.
  • 新 run 记录 parent run、触发消息和 thread root, 方便回放.

协作转交因此是可解释的调度动作.

三层抽象#

  • ChannelRuntimeGateway 从当前 run 解析 scope, 并暴露工具.
  • 领域服务负责 task、reaction、collaboration 和 artifact 的业务规则.
  • 事实记录保存消息、任务、reaction、trigger envelope 或 artifact 读取结果.

ChannelRuntimeGateway 按资源域分发:

资源域核心能力
Messages读取消息和线程, 返回 reaction 聚合.
Artifacts列出、检索和读取 published artifacts.
Tasks创建、认领、更新状态、评论.
Agents列出可协作 Agent, 请求协作.
Reactions添加或移除当前 Agent 的 reaction.

所有工具共用同一个 scope 解析逻辑. 新增工具不会在 Executor 里再扩散成多个彼此独立的内置服务.

取舍#

方案问题Poco 的选择
解析 Agent 输出里的 @handle 自动触发普通提及和真实调度无法区分, 容易循环.不采用.
解析自然语言创建 task脆弱、不可审计、难测试.不采用.
为每种协作语义单独设计工具工具面膨胀, Agent 学习成本高.不采用.
少量结构化频道工具副作用明确、可校验、可回放.采用.

会改变频道状态的动作, 和人类操作一样, 有清楚的系统边界.
