In-sandbox 总体架构#

Poco 把 Agent 执行拆成两个平面. Backend 保存任务、会话、权限、状态和审计数据. Executor Manager 领取并派发 run. Executor 在沙箱里调用模型、文件、shell 和浏览器.

这个边界用来处理长任务失败、工具越权、容器重建和回放审计. 主后端不承接高权限长任务. 执行结果写回 Backend 之后, 才成为后续协作可以引用的事实.

服务分工#

下图是一次请求穿过前端、控制面、调度和沙箱的路径. 蓝色是保存事实的 Backend, 黄色是调度, 橙色是沙箱执行.

前端提交请求, 并读取 Backend 已经聚合的状态. Backend 把请求写成可追踪的事实, 再放进运行队列. 调度器向 Backend 领取的是这次 run 的执行权. 业务库仍留在 Backend. 沙箱里的 Executor 执行完一步, 就用回调把消息、工具调用、状态补丁和产物交回 Backend.

请求穿过边界#

用户请求每过一层, 携带的内容都会变少. 前端保留交互语义, 例如用户输入、当前会话位置和需要展示的状态. Backend 把它写成一条消息、一次 session、一个 run, 以及这次 run 的权限和配置快照.

Executor Manager 领取 run 时, 拿到的是够执行用的快照, 包括 preset、工具、挂载和容器策略. 它不读取整份业务数据库. Executor 开始执行后, 通过回调交付消息、工具调用、状态补丁和导出产物, 不直接改频道、任务或 artifact 表.

越靠近执行层, 拿到的能力越具体、越短期、越容易撤销. 越靠近控制面, 保存的事实越稳定, 也越适合审计.

长任务的六步#

下图按时间列出一次长任务从创建到回写的六步. 颜色和上一张图相同: 蓝色写事实, 黄色做调度, 橙色在沙箱里执行.

服务之间传递的执行契约是 run snapshot. 它包含运行配置、权限模式、会话范围、容器策略和回调地址. Executor 按这份契约运行, 不直接修改 Backend 的数据库.

三个基础边界#

  • 业务事实 以 Backend 为准. server、channel、message、task、agent identity、run 状态、tool execution 和 artifact 索引都写在这里. Executor 完成某个动作之后, 要等回写落库, 前端和后续 Agent 才把它当作事实.
  • 调度 由 Executor Manager 负责 claim、staging、容器选择和 dispatch. 它可以缓存运行准备信息, 也可以处理重试和租约. 频道语义、任务语义和 Agent 私有状态留在 Backend.
  • 执行风险 落在沙箱里的 Executor. 它运行 Agent SDK、MCP 工具、shell、文件和浏览器, 同时限制在当前 run 的权限、挂载和回调契约内.

四个对象#

对象核心职责
Session表示一段 Agent 对话或任务上下文.
Run表示一次可调度执行, 带状态、权限和配置快照.
Dispatcher领取 queued run, 准备执行环境, 调用 Executor.
Execution event把消息、工具调用、状态和产物回写到事实源.

Session 表示这段工作属于哪个上下文. Run 表示这次执行处于什么状态. Dispatcher 把 queued run 送进运行时. Execution event 记录执行过程中发生了什么. 工程上可以先不拆成四个进程. 保存业务事实和运行高权限工具, 仍然要落在不同对象上.

取舍#

方案问题Poco 的选择
Backend 直接运行 Agent主后端承接长任务、工具权限和模型运行风险, 故障域过大.不采用.
单服务同时调度和执行恢复、扩容、隔离和观测都会变重.不作为长期结构.
Control Plane + Sandbox Data Plane服务边界更多, 事实源、调度和执行风险更清楚.采用.

后面增加频道协作、持久化 Agent、公共成果树和模型访问治理时, 事实状态的归属可以沿用同一套边界.

三层微服务通信与状态事实源#

长任务里更容易失控的地方, 是运行中由谁保存事实. Agent 会持续产生消息、工具调用、状态补丁、文件产物和错误. 这些记录如果散落在执行进程、调度进程和前端缓存里, 回放、重试、取消和权限判断会缺少同一份依据.

Poco 让 Backend 保存事实. Executor Manager 领取和派发 run. Executor 执行并上报. Frontend 读取 Backend 聚合后的状态.

领取和回写#

下图只看一次 run 怎样被领取, 以及回调回到 Backend 之后由谁判定. 黄色的租约和快照是调度器拿到的执行权, 蓝色的判定仍在 Backend.

Executor 可以报告事实, 不能成为事实源. Executor Manager 可以准备环境, 不把频道或任务语义收进调度层. Frontend 展示 Backend 给出的状态, 不自己推断任务是否完成.

Backend 保存三类事实#

事实类型例子为什么集中保存
协作事实server、channel、message、task、agent membership权限判断和历史追溯都要读同一份记录.
运行事实session、run、状态机、租约、失败原因重试、取消、恢复和调度去重依赖它.
过程事实tool execution、state patch、workspace export、artifact 索引回放、审计和后续 Agent 复用依赖它.

Executor 如果直接写业务表, 就要理解 server、channel 和 task 的权限与生命周期. Executor Manager 如果持有这些语义, 会从调度器膨胀成第二个后端. 这些语义留在 Backend, 另外两层只处理自己的职责.

Run snapshot#

Backend 创建 run 时, 把当次执行需要的配置固定成 snapshot. 它通常包含 preset、权限模式、容器模式、文件系统模式、server/channel scope、trigger context 和回调上下文.

这份 snapshot 做三件事:

  1. 调度器不必来回拼业务对象. Executor Manager 用 snapshot 就能准备运行环境.
  2. 沙箱拿到的是运行契约. Executor 不直接读 Backend 数据库.
  3. 回放能解释当时的配置. 后来的人能看到这个 run 当时用了哪份 preset、权限和容器策略.

频道消息、thread、artifact、task 和 reaction 的最新状态, 仍然通过 Backend 的受控接口读取.

失败时的两类记录#

Executor Manager 可能在 claim 之后崩溃. Executor 可能在开始执行后断连. Callback 可能重复到达. workspace export 可能比终态消息更晚到达.

Poco 把 “还能不能继续调度” 和 “已经发生了什么” 分开记:

  • 租约、status 和 attempts 描述这个 run 还能不能被重新领取.
  • Agent 消息、tool execution、state patch 和 workspace export 描述执行过程里已经产生的事实.

重复 callback 不创建多份互相矛盾的状态. 延迟 callback 不覆盖更新的终态. Backend 同时看得到 run 状态、session 状态、队列项和回调内容, 才能判断一次回写是新事实、重复事实, 还是过期事实.

回调写入过程事实#

Executor 在运行中持续回写模型消息、工具调用、todo 状态、当前步骤、workspace export、错误和完成状态. 下图是这些回调进入 Backend 之后写成的几类记录.

Backend 用这些记录更新 run 和 session 的当前状态, 同时保留过程数据, 供回放和增量展示. 执行进程可以失败重启, 前端也可以刷新页面. 读者看到的事实, 以 Backend 聚合后的状态为准.

四类边界#

边界核心语义
Create run写入 session 和 run, 并返回可追踪 id.
Claim run调度器领取 queued run, 并获得租约和 snapshot.
Execute runExecutor 接收 snapshot、prompt 和 callback contract.
Submit callbackExecutor 回写消息、工具、状态、产物和终态.

Create run 归 Backend. Claim run 归调度租约. Execute run 归执行环境. Submit callback 归过程事实. 这四类边界稳定之后, 再加推送通知、SDK 缓存、执行抽屉或公共成果树, 基本职责不用重划.

取舍#

方案问题Poco 的选择
Executor 直接更新业务状态执行面必须理解全部权限和协作语义, 故障会污染事实源.不采用.
Executor Manager 持有业务语义调度层变成隐形后端, 恢复和演进都困难.不采用.
Backend 事实源 + Manager 调度 + Executor 执行多一次通信, 职责、恢复和审计边界清楚.采用.

Backend 决定事实. Manager 决定何时跑. Executor 决定如何跑.

LLM Gateway 与模型访问治理#

业务事实和沙箱执行已经分开. 模型访问还需要再收一层. Executor 负责运行 Agent 和工具, 不长期持有 provider key, 也不做成本、路由、限流和审计的最终决定.

LLM Gateway 是控制面上的演进方向. Executor 只拿到 run-scoped token. 模型真实密钥、provider 选择、审计记录和成本控制都收在 Gateway. 沙箱被重建、回收或出现异常时, 模型访问的长期风险留在控制面.

请求怎样穿过 Gateway#

下图是一次模型请求的路径. 紫色的 Gateway 负责鉴权、路由和审计. 它不代替黄色调度层里的 Executor Manager.

Executor Manager 仍然负责调度和环境准备. Gateway 只负责模型访问. 两类职责放在一起, 调度层会同时承受运行生命周期和模型治理.

Run-scoped token#

run-scoped token 表达三类约束:

约束含义
身份约束这个请求来自哪个 run、session、agent 和用户.
能力约束可以调用哪些模型、工具模式或上下文通道.
时间约束token 只在当前执行窗口内有效, 过期后必须重新签发.

沙箱不需要知道真实 provider key. Gateway 根据 token 选择模型、注入真实密钥、记录调用元数据, 并在越界时拒绝请求.

三次校验#

一个模型请求穿过 Gateway 时, 至少经历三次校验:

  • 身份校验 确认 token 由控制面签发, 仍在有效期内, 并且绑定当前 run 和 session.
  • 策略校验 确认这个 preset 或 server 允许调用目标模型, 并且没有超过预算、速率或并发限制.
  • 审计校验 确认请求、响应、错误、耗时和 provider 路由能归属到具体 run.

模型调用因此成为平台级资源访问. Executor 仍然只关心怎样运行 Agent. Gateway 让模型访问可撤销、可追踪、可限流.

分阶段落地#

第一阶段把 Gateway 做成 Backend 内部模块. Executor 的请求仍然打到控制面地址, 由 Backend 的模型代理完成鉴权、路由和审计. 这一阶段先建立 token、审计字段和调用边界.

第二阶段把 Gateway 独立成服务. Backend 负责签发 token. Gateway 负责 provider 连接、限流、成本统计和模型策略. Executor 的调用方式保持不变.

第三阶段再考虑多 provider 策略、按 server 或 preset 的配额、模型 fallback、成本预算和审计查询. run-scoped token 和 Gateway 入口保持稳定, 治理能力可以逐步加上.

三个抽象#

抽象作用
Run-scoped credential把沙箱能力限制在一次运行窗口内.
Provider route把模型选择、fallback 和真实密钥注入留在控制面.
Model call record把成本、错误、耗时和请求归属到 run、session 和 agent.

Gateway 第一阶段不需要复杂路由算法. 先做到长期密钥不进入沙箱, 并且每次模型调用都能归属到 run, 再扩展策略.

取舍#

方案问题Poco 的方向
Provider key 下发到沙箱密钥暴露面大, 审计和吊销成本高.不建议.
Executor Manager 代理模型调用调度层混入模型治理, 边界变重.不建议.
Control Plane 侧 LLM Gateway多一次代理, 密钥、路由、审计和成本可以统一治理.推荐演进.

Gateway 第一天不必承担全部模型平台能力. 它把模型访问从沙箱内部行为, 收成控制面可以治理的资源.
