引言#

模型发出一次工具调用, 就停住这一轮生成. 它要等工具返回, 获取结果之后再发下一次请求. 它把调用一次次串起来, 就要把等待一段一段加起来. 它每获取一次结果, 就要再做一次推理, 并把指令和已经变长的历史重新送一遍.

Anthropic 在 2025 年 11 月的 Advanced tool use 里说明了这一成本, 并主张用程序化工具调用 (Programmatic Tool Calling, PTC) 去掉中间的推理. 获取结果之后, 模型再用自然语言看数据、决定下一步, 五次工具就是五次推理. 这篇说明里, 每次往返的推理要几百毫秒到数秒. 模型把 20 多次调用写进同一段程序, 就省掉其间 19 次以上的推理. 它仍把工具交给接口执行, 把中间结果留在沙箱里, 只看程序最后打印的内容. 模型把循环、对工具返回的筛选和提前退出留在这次执行里. 沙箱没有文件和网络, 模型要读文件或执行命令时, 仍在程序里发起工具调用.

下图对比同几次工具调用时, 结果怎样回到模型. 蓝色是模型, 灰色是一次工具调用, 黄色是程序, 绿色是留在程序里的中间结果.

2026 年 10 月, 三家 agent 相继实现了 PTC. 它们放进 PTC 的工具不同, 完整定义进入请求的方式也不同.

  • Pi 1.0 于 10 月 1 日推出. Pi 在接入 MCP 服务器时打开 codemode, 用 QuickJS 运行 PTC. Pi 默认不把这些工具声明给模型, 让脚本调用它们, 只把打印结果交回模型.
  • OpenCode 2.0 于 10 月 12 日推出 execute. OpenCode 用自写解释器运行 PTC, 按预算把 MCP、浏览器和会话的签名放进目录, 再让 search 按页交回装不下的签名. OpenCode 把 read、edit 和 shell 留成模型的逐次调用.
  • Droid 1.0 于 10 月 29 日推出 Script: 把读文件、修改和执行命令的方法设成 PTC, 先在请求里放短索引, 用到再把完整定义接到请求末尾.

下图对比三家把预算外的完整定义交给模型的方式. 绿色还不是工具定义, 蓝色写进下一次请求的工具定义, 黄色作为工具结果回到对话.

接下来按推出顺序介绍这三家的内部机制.

Pi 1.0#

codemode#

Pi 把 PTC 实现为名为 codemode 的工具. 模型传入的是原始 JavaScript 源码; harness 在 QuickJS 里把它当作 async 函数体执行. 沙箱没有 Node API、本地文件系统、网络或定时器, 脚本只能通过 tools 和 models 访问外界:

  • 会话里每个工具对应 tools 下的一个方法, 例如 tools.read、tools.bash、tools.edit 以及 MCP 映射名;
  • models 用来查目录并按会话凭证调用非对话类模型: 分类器 (models.classify, 对 JSON 或图片做选择题、打分、是/否判断) 和图像模型 (models.generateImages). 目录里也会列出 chat 模型, 但脚本不能从 codemode 里再发起一轮 LLM 对话.

输出由 text()、image()、顶层的 return 和 console 块组成; 只有这些内容作为 codemode 的结果回到对话. store / load 可在多次 codemode 调用之间保留小 JSON. 细节见官方文档 Codemode.

接入的 MCP 默认不声明给模型. 有这类服务器时, Pi 会打开 codemode. 没有 MCP 时, Pi 要用户在默认工具里加上 codemode, 才会提供这段脚本. 写进 codemode 描述的声明大约有 3000 个估算 token 的预算. 脚本只在描述里列出预算内的工具, 再用查找去取预算外的.

脚本按 BM25 做关键词相关度排序, 默认返回 8 条名字和描述. describeTool 返回说明和 TypeScript 声明. 下面的伪代码展示先查再调用.

为什么用 JavaScript 沙箱, 而不是简单的 bash?

Phil Schmid 的说明 在 Why a JS/Python sandbox instead of just bash? 一节里归纳了相对纯 shell 编排的几条理由.

  • 类型化接口: MCP 和内部 API 映成 await tools.*(args), 可用 Promise.all 和 try/catch, 不必在 shell 里转义 JSON 和参数.
  • 少用探索轮次: 模型拿到 bash 里的自定义 CLI 时, 常先跑 --help、读脚本源码才敢调用; TypeScript 声明给出契约, 可以直接写调用.
  • 多模态: shell 只有 stdout 文本, 看图还要单独 read 工具; 沙箱里可以 image() 把像素交回下一轮.
  • 策略代理: 每次 await tools.* 都经过宿主, 可以注入 OAuth、校验 schema、在破坏性操作前暂停.
  • 状态: 大结果不必每轮塞进历史, 可以用 store / load 留在宿主内存里.

工具暴露#

Pi 另外保留一条把完整定义写进下一次请求的入口. 工具的暴露方式决定定义什么时候出现.

  • deferred 先不进请求. 这种暴露方式的工具不出现在当前的工具定义里.
  • tool_search 命中后才声明. 它是模型直接调用的工具, 用同一套排序找尚未声明的工具, 再把命中的定义写进下一次模型调用, 并留在这条会话分支上.
  • only 把内置工具从列表里拿掉. codemode.mode 设为 only 时, 模型只能经脚本调用 read、bash、edit 和 write. 默认的 on 仍把这些工具直接声明给模型, 并在描述里补一句脚本中的调用方式.

OpenCode 2.0#

预算目录和分页搜索#

OpenCode 的 execute 使用自写解释器. MCP、浏览器和会话的 schema 默认留在脚本的目录里. read、edit 和 shell 仍是模型直接调用的工具, 权限照旧.

目录按 4 个字符计一个 token, 把预算定在大约 2000 个估算 token. 目录列出每个命名空间和其中的工具数量, 再按命名空间轮流写入完整签名, 直到预算用完. 预算够时, 目录标成完整. 模型照着清单调用. 预算不够时, 脚本在提示词里看不到其余签名, 再用 search 去取.

search 查的是这次执行已经建好的内存索引, 不访问网络. 它是解释器里的同步函数, 默认一页 10 条. 模型调用时写成 search(...), 不走 tools.search. search 按大小写边界和非字母数字切开查询, 再按路径、说明和参数名打分. 下面的伪代码展示翻页.

Droid 1.0#

与前两者的差异#

Droid 的 PTC 入口叫 Script. 沙箱里写 JavaScript、经工具桥接读写与命令, 与 Pi codemode 同属上文那一类;

分工上的差别有三处:

  1. 读文件、修改和执行命令 对 GPT、Claude、Kimi 等前沿型号默认主推在 Script 里完成; 模型仍可逐次调用, 但首次请求里的工具定义很少. Pi 在默认 codemode.mode: on 下仍把 read、bash、edit 和 write 单独声明给模型, 脚本里另有 models 可跑分类器与出图. OpenCode 把 read、edit 和 shell 留在 execute 之外.
  2. print 回传有上限, 完整工具结果写入日志, 模型之后可以再搜索, Pi codemode 则主要靠 text() / return 和临时文件路径交回.
  3. 短索引与 Deferred Context Engine 确定工具定义何时进请求, 机制见 后文.

过滤与提前退出#

Factory 用一次 修测试的回放 比较了两种走法. 同样 15 次工具调用, 逐次调用用了 10 次模型请求, Script 用了 5 次. 这次回放省下了模型往返. 模型仍要跑多轮程序, 才能做完这个任务.

短索引#

Droid 把完整的工具定义留到后面的请求. Deferred Context Engine 把发现和执行分开. 每轮请求里的索引负责发现, 后来补上的定义负责调用.

  • 每轮先放短索引. 索引里放名字、短描述、来源, 以及够判断相不相关的输入提示, 不放完整 schema 和技能的长说明.
  • 确认之后再提升. 模型认为某项能力用得上时, 调用内置的扩展工具, 把完整 schema 或技能说明加载进来.
  • 提升后的定义接在请求末尾. Droid 把提升后的定义接在请求末尾, 保住已经缓存的前缀. 模型在剩余工作里一直看得到这项工具, 可以直接调用, 也可以写进 Script.

整套 harness#

Script 之外, 这套 harness 还改了请求怎么增长、首次请求放多少工具, 以及卡住时谁来决定下一步.

  • 请求尽量只追加. Droid 让前缀继续命中提供商的缓存, 把中途新出现的工具定义接在末尾, 以免改写这个前缀.
  • 首次请求少放工具定义. Droid 把首次请求里的工具定义 从 11 个减到 2 个, 其余用到再加载.
  • 卡住时由循环接手. 循环在重复调用、流中断或长时间无输出时接手, 自己决定重试或停止.

分析对比#

下图是 Factory 公布的 Terminal-Bench 4 结果, 同一模型下比较各家 harness. 横轴往右更便宜, 纵轴往上通过率更高.

Droid 在两张图里的通过率都更高. GPT-6.1 Sol 上, 它的单题成本和 OpenCode 靠近; Opus 5.5 上, 它还更便宜. 这次评测 的 OpenCode 是 2.1.2, 已经有 Code Mode. 其余对照没有 PTC.

v.s. 默认 harness#

Droid 与默认 harness 的差异在有没有 PTC. Codex、Claude Code 等传统 harness 让模型逐次调用工具, 每次结果都回到下一次请求. Droid 有 Script, 模型把多次调用写进一段程序, 循环和核对在程序里执行.

相对 Droid 自己的逐次调用, Script 在 Opus 5.5 上把成本降了 15%. 大多数 Script 很短. 省下的成本集中在调用不少于 6 次的那 12.5%.

这些没有 Script 的 harness 伴随着普遍较低的 pass rate 和较高的平均成本, 这说明同一模型下加上 PTC 是可行的.

v.s. OpenCode#

OpenCode 和 Droid 都有 PTC, 底层实现不同, 导致了二者在 bench 表现上的差异:

  • OpenCode 的 execute 用自写解释器, 调用 MCP、浏览器和会话; read、edit 和 shell 仍是逐次调用, 目录靠预算和 search 分页.
  • Droid 的 Script 跑在没有文件和网络的沙箱里, 读文件、修改和执行命令默认也在程序里调用. 完整定义先放短索引, 用到再接到请求末尾, 已经缓存的前缀还能命中.

我的猜测是, 这两张图上的差距还可以从三处实现看.

  1. 首次请求的工具定义从 11 个减到 2 个. Factory 量过空会话的首次请求, 输入 token 从 20,887 降到 13,055, 工具定义从 15,798 降到 8,528. 这两次发布跑在不同模型上, 按字符计是从 57,035 降到 36,802. 这份前缀会留在后面每一次请求里. 前缀短一截, 每一轮的输入 token 都少一截, 单题的输入成本下降. Factory 写过, 多放进请求的说明会在之后每一轮分散模型的注意. 用不到的定义不再每轮出现, 模型少被带去调用这些工具, 更不容易漏做题目要求的步骤. 漏做步骤的题目变少, 通过率更高.

  2. 新的工具定义接到请求末尾, 已经缓存的前缀继续命中. Factory 在 Azure 上对比过一次加载工具, 接在末尾时 26,400 个 token 全部从缓存读出. 定义若插进列表前部, 前缀在插入处断开, 后面的对话要整段重新处理, 这一轮的输入成本接近把已有对话再付一遍. 单题成本里有这一笔.

  3. 循环可以提示并减少重复的调用. 第三次相同的工具调用, 循环发出提醒, 模型下一次可以改做别的步骤, 这道题还有机会做完. 第六次仍相同, 循环停止, 不再为这次重复发出后面的请求. 流中断时循环重试, 并先删掉半截回答, 模型只在完整回答上继续, 少从残缺输出把这道题做偏.

小结#

Pi 的 codemode、OpenCode 的 execute 和 Droid 的 Script 都是 PTC. 模型用代码规定调用顺序, 把循环、过滤和分支留在这次执行里. 它少做一次推理, 也少把指令和已经变长的历史再送一遍, 工具调用的往返成本因此下降.

PTC 出现, 个人认为得益于模型的编与规划能力的增强. 规划是它在结果返回之前, 就把分支条件写进同一次请求. 编排是它按这些条件, 把下一跳工具调用接上去.

同时这也带来一个启发: 在与 agent 进异步协作的过程中, 如果我们的提示词也 Script 一样包含了严谨的条件分支与多跳逻辑, 是不是也会更加高效?
