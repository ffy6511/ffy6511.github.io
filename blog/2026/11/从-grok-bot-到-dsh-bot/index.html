订阅了四个月的 grok 生态体验#

从 build 到 bot#

七月初我从第一家实习公司离职, 失去了 AI 订阅半价报销, 手头紧. 在职时连续订阅了几个月的 ChatGPT 20x 不说人话且喜欢极端防御性编程, 此时恰好迎来了 grok build 的三个月订阅优惠, 最高档从 300 美元降到 100 美元, 我抱着尝鲜不亏的心态加入了 grok 生态.

Grok Build 作为 TUI, 比我之前用过的 agent TUI 都顺手; 配上 herdr 之后, 多会话并发时效率也很高.

印象里 grok bot 是八月才正式推出的. 早期的 grok build 订阅还附送 Cursor Ultra (可以用 Opus 和 Fable, 虽然额度很少), 以及 X 会员; 当时 grok 响应快, 性能也不落后. 只看 build 这一项, 订阅就已经物超所值.

grok bot 上线后, 我第一次可以在手机上统一管几台机器: bot 附带的一台 linux 主机、实验室的 Mac mini、随身带的 MacBook Pro, grok bot 是主入口. 当时还在社媒上惊叹工作流的变化:

这里用到 uu 远程是因为, 虽然 mini 开启了永不休眠, 但是当时 grok bot 客户端不在前台的时候, 会隔段时间掉线. 所以用 uu 远程通过手机唤醒或者写个定时脚本拉取到前台更保险一些.

探索 grok bot#

下面不少操作的启发来自于 X 上的帖子和讨论, 我会尽量贴上链接.

与 X 的联动#

grok bot 账号与 X 联通之后, 在 X 上 @bot 就能把消息发到我的主 bot. 例如在 这条帖子 下回复 “帮我按照这个思路操作”, 背后的 grok bot 用主机上的 GitHub CLI 跑完备份, 并配置了定期备份任务:

我还建了一个 Daily Flow bot: 每天把 X 书签里标为 to read 的帖子整理成日报 (再移到 done 书签), 写入飞书文档. 飞书这边的好处是, 任务可以在主机或实验室的 mini 上用 lark-cli 写文档, 不必等我带着 MacBook Pro 起床才跑 cron.

grok bot 的飞书插件在国内似乎不可用, 看起来面向海外 Lark, 所以我用 lark-cli 代替.

为什么从 X 收素材

Daily Flow 读的是 X 书签, 因为科技圈的新工具、评测和用法往往先在 X 上流转. 把 X 当作科技讯息入口, 是我入职字节时同事 Oanakiaja 帮我建立起来的习惯. 举几个近期看的例子:

  • poteto 在 X 上分享的 pstack 侧重 agent 的工程化 (verification skill、/poteto-mode 按任务选 playbook 等);
  • Addy Osmani 也会转发 Anthropic 团队的实践长文, 例如 claude.dev 上的 How the Claude Code team does code review.

社区里同样能看到 grok bot 备份 repo、lark-cli 替代飞书插件这类实操帖.

自动备份配置#

#与 x 的联动 里的例子提到, grok bot 可以通过 GitHub repo 自动备份 bots 定义、记忆和 skill. 另一种玩法是改 repo 里的配置, 再让 bot 拉取, 间接更新 bot 本身.

绕 repo 更新, 是因为 grok bot 客户端虽然能看到 bot 的指令、记忆和 skill 详情, 但不能像编辑文档一样直接改; 例行任务也一样: 有的自动化可以点进去看配置和说明, 有的条目点了没反应. 所以要改配置, 往往得在聊天里口述, 或走 repo 拉取. 用久之后上下文容易腐化, 只能反复声明规范, 再祈祷跑定时任务时别忘掉约定🙏. 这成了我后来换平台的重要理由之一.

顺带一提, 聊天里键入 / 调不起 skill; 我必须在 Mac 上用 cmd+shift+M (不问 ai, 无从得知的入口) 打开一个正常点击进不去的 skill 面板, 抄名字再粘贴…

通过 herdr 使用 coding agent#

手机上的 grok bot 适合派活, 但 coding agent 仍要跑在本机 workspace 里. 我把它和 herdr 接起来: bot 经用户批准的远程 shell 在 mbp 或实验室 mini 上调用 herdr agent start / prompt, 默认开 Grok Build 会话. herdr 的 integration install grok 会通过 SessionStart hook 上报 session id, 屏幕检测则覆盖 idle / working / blocked / done 等状态.

agent 进入 done 或卡在 blocked 时, 监听脚本把最后一段输出 POST 到 webhook routine, 再唤醒 grok bot 决定下一步. 我回到电脑前, 可以在 herdr 里直接查看对应 pane 并接手.

下面是我放在 fstack 里对应的 skill, 涵盖了上述流程的操作步骤:

scripts/grokbot-notify.sh
#!/bin/bash
# 监听 herdr agent；完成/卡住时把最后输出 POST 给 Grok Bot webhook routine
# 触发：done、blocked，以及 working→idle（聚焦 pane 时常跳过 done）
AGENT=${1:-gb1}
ENV_FILE="${GROKBOT_WEBHOOK_ENV:-$HOME/.config/herdr/grokbot-webhook.env}"
if [ ! -f "$ENV_FILE" ]; then
  echo "missing webhook env: $ENV_FILE" >&2
  exit 1
fi
# shellcheck disable=SC1090
. "$ENV_FILE"
if [ -z "${GROKBOT_WEBHOOK:-}" ]; then
  echo "GROKBOT_WEBHOOK empty in $ENV_FILE" >&2
  exit 1
fi
AUTH="${GROKBOT_AUTH:-}"
AUTH="${AUTH#Authorization: }"
AUTH="${AUTH#authorization: }"
case "$AUTH" in
  [Bb]earer\ *) ;;
  *) AUTH="Bearer $AUTH" ;;
esac
LAST=""
SAW_WORKING=0
post_status() {
  local S="$1"
  TEXT=$(herdr agent read "$AGENT" --source recent-unwrapped --lines 60)
  jq -n --arg a "$AGENT" --arg s "$S" --arg t "$TEXT" '{agent:$a,status:$s,text:$t}' \
    | curl -sS -X POST "$GROKBOT_WEBHOOK" -H "Authorization: $AUTH" \
        -H 'content-type: application/json' --data @- && echo "$(date) sent $AGENT $S"
}
while true; do
  S=$(herdr agent get "$AGENT" 2>/dev/null | jq -r '.result.agent.agent_status // empty')
  [ -z "$S" ] && { sleep 10; continue; }
  if [ "$S" = working ]; then
    SAW_WORKING=1
  fi
  if { [ "$S" = done ] || [ "$S" = blocked ]; } && [ "$S" != "$LAST" ]; then
    post_status "$S"
    SAW_WORKING=0
  elif [ "$S" = idle ] && [ "$SAW_WORKING" = 1 ] && [ "$LAST" = working ]; then
    # focused pane: completion often lands as idle without done
    post_status idle
    SAW_WORKING=0
  fi
  LAST=$S
  sleep 2
done

herdr-grokbot#

云端 Grok Bot 通过本机 herdr 驱动本机编程 agent（默认 Grok Build）。Agent 完成或卡住时，监听脚本把最后输出 POST 给 webhook routine，再唤醒 Grok Bot。

  • 每次远程 shell 都要用户批准。
  • pane id 从 JSON 取（workspace create / tab create 的 .result.root_pane.pane_id，例如 w9:p1）。不要猜，不要按侧边栏顺序推。

  • 需要换模型时用该 agent 自己的 CLI 参数（放在 -- 后），不要改用户全局配置。
  • webhook URL 和 Authorization 只放 ~/.config/herdr/grokbot-webhook.env，不要贴进聊天。
  • Cursor Cloud Agent 走各自的 skill，不用这条回路替代。

状态#

状态靠读屏幕，可能停在 unknown。unknown 只说明分不了类，不能当成完成。

  • idle：可以输入，且该 tab 已在聚焦的 herdr UI 里看过。
  • done：后台工作结束、UI 还没看过，底层与 idle 相同。在 UI 里看过该 tab 之后变成 idle。CLI read 不会把它标成已看。
  • blocked：批准框或提问。
  • working：正在跑。

CLI 错误是 stderr 上的 JSON，退出码 1。

回调#

Grok Bot 建一个 webhook 触发的 routine。用户从 routine 面板复制 Webhook URL 和 Authorization header，写到 ~/.config/herdr/grokbot-webhook.env：

值必须加引号。GROKBOT_AUTH 用 Bearer 前缀；脚本也会在缺前缀时自动补上。

然后在本机跑（参数是 agent 名，默认 gb1）：

脚本轮询 herdr agent get。状态变成 done 或 blocked 且与上次不同时，用 agent read --source recent-unwrapped --lines 60 取最后输出，POST JSON {agent, status, text}。GROKBOT_AUTH 若带 Authorization: 前缀，脚本会去掉再放进 header。空状态（server 还没起来）每 10 秒重试，其余每 5 秒看一次。

herdr 不会主动 webhook，所以这条回路用轮询。下列项可能仍未在你这台机器上验证：

  • webhook 实际 POST 能唤醒 routine
  • 用插件事件 pane.agent_status_changed 代替轮询
  • 各 agent 自带的 notify / Stop hook 作为替代

操作要点（给执行这条 skill 的 Bot）#

  1. 先确认本机 herdr server 活着（herdr agent list），再布局 / start。
  2. 多任务先 workspace list：有可复用的就 tab create --workspace …，没有才 workspace create。禁止「一个任务一个 workspace」。
  3. 默认 --kind grok、agent 名 gb1（并行时用唯一名如 gb251）；用户点名其他栈时再改，并同步改 notify 脚本参数（可每 agent 一个 LaunchAgent）。
  4. 每条远程 shell 都走用户批准；批准框内容先 read 再决定是否 y。
  5. 任务结束后若用户已配 webhook，提醒本机保持 grokbot-notify.sh 在跑；未配则读屏后把摘要直接回给用户。

# herdr-grokbot

云端 Grok Bot 通过本机 [herdr](https://github.com/herdrdev/herdr) 驱动本机编程 agent（默认 **Grok Build**）。Agent 完成或卡住时，监听脚本把最后输出 POST 给 webhook routine，再唤醒 Grok Bot。

herdr 是 Rust 写的、面向编程 agent 的终端复用器。文档 <https://herdr.dev/docs>。server 托管 pane，识别状态 `idle` / `working` / `blocked` / `done` / `unknown`。控制面是 CLI，本地 unix socket `~/.config/herdr/herdr.sock`（每行一个 JSON）。没有 HTTP API，不会主动发 webhook。

## 默认 agent（可覆盖）

| 项 | 默认 | 说明 |
| --- | --- | --- |
| herdr `--kind` | `grok` | 检测清单里 `grok-build` 是别名，CLI 用 `grok` |
| agent 名 | `gb1` | 须匹配 `[a-z][a-z0-9_-]{0,31}`，且在存活 agent 中唯一 |
| 可选集成 | `herdr integration install grok` | SessionStart hook；状态仍主要靠屏幕检测 |

用户说「用 Codex / Claude / …」时，把 `--kind` 和 agent 名换成对应值（例如 `codex` + `cx1`）。不确定时跑 `herdr agent` 看本机支持的 kind 列表，不要臆造。原生参数一律放在 `--` 后面，且不要改用户家目录里的全局配置文件来迁就某次任务。

## 搭建

1. 安装：

```bash
curl -fsSL https://herdr.dev/install.sh | sh
herdr integration install grok   # 默认 Grok Build；换 kind 时改装对应 integration
```

2. 常驻 server。直接 `herdr server &` 会随启动它的 shell 退出而死：

```bash
launchctl submit -l dev.herdr.server -o /tmp/herdr-server.log -e /tmp/herdr-server.log -- ~/.local/bin/herdr server
herdr agent list
```

3. **布局：优先同一 workspace 的不同 tab。** herdr 里 workspace ≈ 侧边栏的 space；tab 是 space 里的标签页。

- **第一次**（或还没有合适的 workspace）：建一个 workspace，记下 `.result.workspace`（如 `w9`）和 `.result.root_pane.pane_id`：

```bash
herdr workspace list
herdr workspace create --cwd <dir> --label <workspace-label> --no-focus
# → .result.workspace / .result.tab / .result.root_pane.pane_id
```

- **同一工作流里的第 2、第 3… 个任务 / 会话**：复用已有 workspace id，只加 tab（不要再 `workspace create`）：

```bash
herdr tab create --workspace <workspace-id> --cwd <dir> --label <task-label> --no-focus
# → .result.tab / .result.root_pane.pane_id
```

约定：并行 issue（如 ageval `#251`/`#252`/`#255`）共用一个 workspace（例如 label `ageval-parallel`），每个 issue 一个 tab + 一个 agent 名（`gb251`、`gb252`…）。只有用户明确要求隔离、或 cwd/环境完全无关时，才新开 workspace。

4. 启动本机 agent（默认 Grok Build）。原生参数必须放在 `--` 后面。`agent start` 要的是已有的空闲 shell pane，不会自己建 pane：

```bash
herdr agent start gb1 --kind grok --pane <pane>
# 用户指定其他 kind 时，例如：
# herdr agent start cx1 --kind codex --pane <pane> -- -m gpt-5.5 --sandbox workspace-write --ask-for-approval on-request
```

5. 新目录首次可能弹 trust / 确认：`start` 返回 `agent_not_ready`（blocked）。名字仍可用于 `read` / `send-keys`。键名用大写 `Enter`，小写 `enter` 无效：

```bash
herdr agent send-keys gb1 Enter
```

6. 发任务。`--wait` 等到第一次落到 `done` 或 `blocked`（也会落到 `idle`）。超时单位毫秒：

```bash
herdr agent prompt gb1 "..." --wait --timeout 600000
herdr agent read gb1 --source recent-unwrapped --lines 60
```

7. 批准框：`prompt` 返回 `blocked` → 先 read 看命令 → 确认安全后：

```bash
herdr agent send-keys gb1 y
```

紧接着的 `herdr agent wait gb1` 会立刻返回旧的 `blocked`（当前状态已经匹配，wait 不会等它变化）。sleep 几秒，再用 `herdr agent get gb1` 轮询 `.result.agent.agent_status`。

## 状态

状态靠读屏幕，可能停在 `unknown`。`unknown` 只说明分不了类，不能当成完成。

- `idle`：可以输入，且该 tab 已在聚焦的 herdr UI 里看过。
- `done`：后台工作结束、UI 还没看过，底层与 `idle` 相同。在 UI 里看过该 tab 之后变成 `idle`。CLI read 不会把它标成已看。
- `blocked`：批准框或提问。
- `working`：正在跑。

CLI 错误是 stderr 上的 JSON，退出码 1。

## 回调

Grok Bot 建一个 webhook 触发的 routine。用户从 routine 面板复制 Webhook URL 和 Authorization header，写到 `~/.config/herdr/grokbot-webhook.env`：

```bash
GROKBOT_WEBHOOK="https://…"
GROKBOT_AUTH="Bearer <sender-key>"
```

值必须加引号。`GROKBOT_AUTH` 用 `Bearer ` 前缀；脚本也会在缺前缀时自动补上。

然后在本机跑（参数是 agent 名，默认 `gb1`）：

```bash
# 相对本 skill 目录
scripts/grokbot-notify.sh gb1
```

脚本轮询 `herdr agent get`。状态变成 `done` 或 `blocked` 且与上次不同时，用 `agent read --source recent-unwrapped --lines 60` 取最后输出，POST JSON `{agent, status, text}`。`GROKBOT_AUTH` 若带 `Authorization: ` 前缀，脚本会去掉再放进 header。空状态（server 还没起来）每 10 秒重试，其余每 5 秒看一次。

herdr 不会主动 webhook，所以这条回路用轮询。下列项可能仍未在你这台机器上验证：

- webhook 实际 POST 能唤醒 routine
- 用插件事件 `pane.agent_status_changed` 代替轮询
- 各 agent 自带的 notify / Stop hook 作为替代

## 操作要点（给执行这条 skill 的 Bot）

1. 先确认本机 herdr server 活着（`herdr agent list`），再布局 / start。
2. **多任务先 `workspace list`：有可复用的就 `tab create --workspace …`，没有才 `workspace create`。禁止「一个任务一个 workspace」。**
3. 默认 `--kind grok`、agent 名 `gb1`（并行时用唯一名如 `gb251`）；用户点名其他栈时再改，并同步改 notify 脚本参数（可每 agent 一个 LaunchAgent）。
4. 每条远程 shell 都走用户批准；批准框内容先 read 再决定是否 `y`。
5. 任务结束后若用户已配 webhook，提醒本机保持 `grokbot-notify.sh` 在跑；未配则读屏后把摘要直接回给用户。

再见了 grok build#

十月起 grok 把 grok build、Cursor 和 grok bot 合成一档订阅, 标价从 300 美元降到 200 美元. 首月半价, 加上 Codex 还在做 28 天活动疯狂重置给出无法使用的额度, 我又用 100 美元续了 grok.

额度比预期花得快, Cursor 里 “量大管饱” 的时代结束了:

  • 第一周第二天就用掉 50% 周限额, 剩下几天靠 magpie 到处”捡垃圾”勉强果腹;
  • 第二周 (写这篇 blog 的时刻) 的前两天跑到 80%, 大部分额度是用在纠正上下文腐化、记忆错乱的自动化. 又硬撑两天后, 额度还是见底😭:

我只好另找 personal agent 的方案.

为什么是 dsh bot#

项目 repo 叫 ds-bot, 但是作为 DeepSeek Harness (DSH) 插件, 我还是习惯称其为 dsh bot.

十月初我也试过别的 bot, 效果都不理想. 例如 OpenMausBot 才两百多 star 时我就在 X 上看到宣发并试用, 但几个 coding agent 的输出都有问题, 感觉小团队开源还需要时间打磨.

之后 dsh 生态里的插件变多, DSH 迭代也相对稳定, 我开始关注这块, 其中包括 DS-Bot.

迁移到 dsh bot#

迁移很简单: 把 grok bot 定时备份的配置 repo 发给 dsh bot 即可.

bots 的 profile (描述、记忆文件等) 大多已在 repo 里. 我让 dsh bot 按需求读 repo, 它反馈有些信息缺上下文; 我又让 grok bot 补了一份 md 交接文档, 就完成了迁移.

一些体验#

bot 不再那么黑盒#

#自动备份配置 里吐槽 grok bot 黑盒的几点, 在 dsh bot 上都得到了比较好的解决: 配置入口更直接.

  1. 自动生成且可编辑的记忆条目

  2. 每个 bot 可以直接配置 skill、工作区和描述.

  3. 定时任务列表和明细更稳定:

有个怪现象: 当前版本里, bot 创建的定时任务有时会只出现在 DSH 自带的 “自动化任务” 里, bot 面板里看不到.

依旧可以与 X 联动#

前文提到, grok bot 靠自家 API 读 X 帖子、整理书签. dsh bot 没有同等的一键集成, 但还能复刻类似流程吗?

第一个 bot 在 zero-shot 下拼出了 ego 浏览器和 lark-cli 的 skill 组合, 自己找到了可行路径, 这还是令我感到惊喜的~

难道说大肥鱼我可以相信你吗😭 不过后续还是通过 magpie 接入其他模型一起用吧😁

TBC#

dsh bot 纵然还有不完善的地方, 例如当前的 远控插件 并不稳定, 同类产品 dsh-go 也还没有完全支持 ios 端. 但是我相信开源社区的力量会将 dsh bot 和 dsh 插件生态打造得越来越好~ 🫶 也会有很多和 dsh bot 交互的体验未完待续…

小结#

从 grok build、grok bot 到 dsh bot, 这四个月里 personal agent 在演进过程中逐渐收敛了它的形态. grok 把 X、手机和本机 agent 串在一起的工作方式令我感到惊喜, 但是他的黑盒性和额度缩水又逐渐将我劝退; DSH 这边更透明, 可配置性更强, 同时迁移成本也不高.

工作流迭代的就是如此之快, 很难说哪一家会一直是主入口, 我大概会继续试、继续改 cron 和 skill, 也期待看到并体验下一轮工作流~
